# Releasing OpenInsert

## Combined macOS and Windows release

The existing v0.3.0 public assets are macOS-only. Do not move or reuse that tag to add this Windows port. Select a new version, update `Resources/Info.plist` and `windows/OpenInsert.Windows/OpenInsert.Windows.csproj`, then update README, validation records and `docs/RELEASE_NOTES.md` to describe the actual published state. Use a clean checkout. The tag (`v<version>`) must match both project versions; Windows accepts a normalized leading `v` and rejects version/path metacharacters.

The [release workflow](../.github/workflows/release.yml) has separate macOS and Windows package jobs. Windows produces self-contained x64 and ARM64 ZIPs, per-user Inno Setup installers, and SHA-256 manifests. macOS retains its universal ZIP/DMG flow. Only one final job creates the draft, after every build succeeds and all downloaded asset checksums match. No job publishes automatically, embeds a Gemini key, installs a code-signing certificate, or requests cloud consent for users. A repeated run will not overwrite an existing release; inspect and resolve an existing draft deliberately before rerunning its publisher.

## Windows checklist

1. On Windows, install the .NET 10 SDK and Inno Setup 6.3 or newer from their official sources. CI uses `actions/setup-dotnet` and the compiler preinstalled on GitHub's Windows runner; `-Installer` fails rather than silently omitting an installer if the compiler is missing.
2. Run the three offline harnesses: `dotnet run --project windows/OpenInsert.Core.Tests -c Release`, `dotnet run --project windows/OpenInsert.Windows.Tests -c Release`, and `dotnet run --project windows/OpenInsert.Platform.Tests -c Release`. Run `./scripts/package-windows.ps1 -Runtime win-x64 -Installer -Version v<version>` and repeat for `win-arm64`. The output is under `dist/windows`. Packaging is self-contained and disables trimming; users do not need to install .NET.
3. Extract each ZIP, inspect `build-info.json` and executable version metadata, and launch the matching architecture's `OpenInsert.exe --smoke-test`. CI runs this on x64 only. Record ARM64 execution separately; successful cross-compilation is not hardware validation. Verify SHA-256 manifests against all final ZIP/setup EXE bytes.
4. Test a fresh per-user installation, Start menu launch, quit, upgrade, uninstall and reinstall as a non-administrator. Ensure shortcuts and uninstall registration behave correctly and settings/the encrypted key survive reinstall. Confirm the portable package works from a different extracted location without a globally installed .NET runtime. Installers retain `%LOCALAPPDATA%\OpenInsert` user data on uninstall.
5. Complete the [Windows validation matrix](WINDOWS.md#validation-status) using a real microphone and your own consented Gemini key. Test ordinary editors, custom shortcuts, privacy denial, cancellation, focus changes, password fields, clipboard ownership and elevated-app fallback. Never report the macOS results as Windows evidence.
6. Public community builds are unsigned until a maintainer configures Authenticode signing. Do not describe them as signed, trusted by SmartScreen, or verified on every supported OS. If signing is added, sign application executables **before** packaging, sign the installer after compilation, timestamp with the signing provider's supported service, then regenerate hashes and verify signatures. Keep certificates and credentials out of source and logs; the current scripts do not implement signing.
7. Test a genuinely downloaded artifact on a clean supported Windows machine. Record the architecture, Windows build, SDK/runtime and Inno Setup version, commit, signing state, failures and untested cases. Publish the combined draft only after reviewing those results and the platform-specific release notes. Self-contained applications carry their runtime: rebuild and distribute updates when the bundled runtime needs servicing.

These are release gates for a maintainer, not claims that the new port has passed every check. Local package tests, CI results and real cloud/microphone tests must be documented with their distinct scopes. See [Microsoft self-contained deployment](https://learn.microsoft.com/dotnet/core/deploying/), [Inno Setup non-administrative privileges](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm), and [the GitHub Windows runner inventory](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md).

## macOS checklist

1. Update Info.plist version/build in step with the Windows project version, README, validation report and release notes. Use a clean checkout.
2. Run `swift test`. Exercise real microphone capture, a real Gemini key and mixed-language speech. Verify no-speech, cancellation, focus changes and permission denial. Update the cross-app matrix; do not mark untested cases as passed.
3. Build `ARCH=universal ./scripts/package.sh`. The working app is `.build/app-staging.noindex/OpenInsert.app`; public ZIP, DMG and checksum files remain in `dist`. DMG staging uses a unique temporary directory under `.build` and is cleaned on exit. Check `lipo -archs`, Info.plist, archive contents and checksums. Intel cross-compilation is not equivalent to an Intel runtime test.
4. For a normal public installer, use **Developer ID Application** signing with hardened runtime. Apple Development or ad-hoc signing is not equivalent. Never put certificates/passwords in the repository.
5. Submit the signed zip using `xcrun notarytool submit <archive.zip> --keychain-profile <profile> --wait`. The maintainer must configure this profile and accept any Apple agreements themselves.
6. After acceptance, staple with `xcrun stapler staple .build/app-staging.noindex/OpenInsert.app`, regenerate the zip/DMG and checksums from that stapled bundle, and notarize/staple the DMG as appropriate. Do not rerun `build-app.sh` or `package.sh` for this archive regeneration: both rebuild and replace the stapled app. Verify with `codesign --verify --deep --strict`, `xcrun stapler validate`, and `spctl --assess --type execute` on the final app. Test a genuinely downloaded artifact on a clean Mac.
7. Publish the draft release only with accurate signing and validation status. The current workflow intentionally makes a draft, ad-hoc-signed early release; it is not a notarization pipeline.

Official guidance: [Apple code signing](https://developer.apple.com/documentation/security/code-signing-services), [notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Gatekeeper](https://support.apple.com/en-us/102445).
