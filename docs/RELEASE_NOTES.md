OpenInsert 0.2.6 / build 8 is under validation and **not released**. It revises accessibility initialization after the internal, unreleased 0.2.5 still failed to obtain the affected ChatGPT/Codex desktop editor's focused element (`AXFocusedUIElement`, -25212).

- Initialization now uses actual `AXManualAccessibility` writable/Boolean capability rather than requiring an `Electron Framework.framework` filename. An already-enabled flag is left alone.
- Only the exact bundle principal class `BrowserCrApplication` permits an `AXEnhancedUserInterface` activation request when Manual is unavailable. Manual permission/transport errors and invalid Boolean data do not permit that fallback. This follows the [Chromium implementation](https://github.com/chromium/chromium/blob/main/chrome/browser/chrome_browser_application_mac.mm#L391-L464); the affected app's metadata indicates a Chromium-based app, not merely renamed Electron.
- Each identified target process launch receives at most one activation write during an OpenInsert run, even if the setter reports an error. Only success starts a three-second preparation window. Valid focus is still required; a successful setter does not prove that the editor is ready. Preparation diagnostics contain metadata and AX status only, without reading input content.

The following delivery changes from the unshipped 0.2.5 are included:

- A completed final result is copied automatically when no valid input target was captured or a supported insertion error occurs before paste dispatch. The floating panel confirms a successful copy for about six seconds without activating the main window; the user can then paste manually.
- This copy intentionally replaces the clipboard and persists, even when normal paste restoration is enabled. Successful standard paste keeps its existing 800 ms restoration and ownership checks.
- Empty text, clipboard-change/read/write failures, cancellation, interim-only output, unhandled or permanent provider failures, unknown errors and errors after paste dispatch do not trigger a second clipboard write. A copy failure reports an error and keeps the finalized text in the app. Existing accepted skip/temporary-cleanup fallback can still deliver finalized ASR through the same paste-or-copy path.
- Focus lookup now tries the global AX focused element first. Only no-value (-25212), unsupported-attribute or not-implemented results permit one app-specific fallback. The current foreground PID and returned-element PID must match the expected app. Secure fields, invalid elements and other errors remain excluded; no UI-tree search or surrounding-text read is added.
- The five-second fixed-text insertion test shares the delivery path, allowing paste and copy behavior to be checked without microphone capture or an API call.

**0.2.6 has passed 105 native XCTest cases, typechecking and universal build checks, but has not yet been installed or tested in the affected editor.** A user previously confirmed the 0.2.4 fixed paste test, then reported the 0.2.5 focus failure; these results do not establish 0.2.6 compatibility. [GitHub CI](https://github.com/Buffett111/OpenInsert/actions/runs/35445093242) also passed unit tests, synthetic PCM checks and universal packaging; release remains on hold. See the separate [validation report](VALIDATION.md).

A paste request still has no OS delivery receipt. No AX transcript write, automatic second paste or Return key is sent. Slow editors may read the clipboard after its restoration window, and embedded terminals may escape terminal detection. Copied results can be retained or synced by clipboard managers and system clipboard features; closing OpenInsert or clearing its result view does not clear the clipboard. See [privacy](PRIVACY.md) and [architecture](ARCHITECTURE.md).

Multilingual dictation and code-switching, existing language preferences, Gemini models, cloud consent, microphone streaming and the absence of screen context/history are unchanged. Public CI builds remain ad-hoc signed and unnotarized unless explicitly configured; personal local signing data is excluded. See [installation](INSTALL.txt).
